# WP-04 Part 1 — rulings

This ledger records every ruling made while planning and executing WP-04 Part 1 (Investigation workbench and Markdown notes), and what each one costs if it is wrong.

- Spec: `docs/superpowers/specs/2026-09-25-wp04-part1-investigation-design.md` (IN1–IN41, owner decisions O1–O7).
- Plan: `docs/superpowers/plans/2026-09-25-wp04-part1-investigation.md` (18 tasks).
- Branch: `feat/wp-04-part1` from `1cba08c`, the PR 1 head after the WP-03 Part 1 polish pass (polish ledger JP8).
- Precedent, all binding: the Part 3–7 ledgers, the Part 7 polish ledger, the WP-03 Part 1 ledger (J, JF, "WP-03 E") and the WP-03 Part 1 polish ledger (PO, JP, JQ, "WP-03 Polish E").
- Numbering:
  - **O1…** are owner decisions;
  - **IN1…** are the spec's decisions;
  - **IP1…** are planning rulings;
  - **IPF1…** are pre-flight rulings;
  - **"WP-04 E1…"** are execution rulings.
- Every ruling reads: **Ruling:** what — why — cost if wrong.

## Owner decisions (2026-09-25, before the spec)

| # | Decision |
|---|---|
| O1 | Part 1 covers all of 04.1–04.7. Clone groups and symbol tracing are deferred. |
| O2 | A new **Investigate** screen (route). Quality, File detail, the city file inspector and Architecture open it on the same finding. |
| O3 | **Notes are the record.** A note is linked to its finding by its own frontmatter, read through Obsidian's metadata cache. No link table; the review format stays v2. |
| O4 | **A folder setting plus a confirm dialog.** Nothing is written until the user confirms the folder and filename. |
| O5 | **No external-editor action** in Part 1. |
| O6 | **Independent status.** The note's `status` is the user's; nothing syncs with review dispositions or work items. |
| O7 | **Notes may be written inside the codebase root**, after an explicit checkbox that adds the folder to the scan exclusions; the README and the two storage disclosures are reworded. |

| IP4 | **Ruling (corrects IN20, S2):** `finding_fingerprint` is written as the portable key `<source_path>#<finding_id>` (the review export's `findingRef`, `src/ui/read-models/review-state.ts:64`), and `entity_id` as `file:<source_path>`. | IP5 | **Ruling (extends IN24, S5):** `noteText` also flattens every line break (CR, LF, U+2028, U+2029) to a space, turns tabs into spaces, replaces C0/C1 controls and bidi/format controls (U+200E/F, U+202A–E, U+2066–9) with U+FFFD, escapes `:` everywhere and the `.` of `www.`, escapes a leading `N)` as well as `N.`, and caps each value at 256 code points before escaping. — IN24 escapes a leading `-` only at the string's start, so a symbol holding `\n# x` would start a heading; bare `https://` and `www.` are auto-linked by Obsidian; `1)` is a CommonMark list opener; bidi controls hide text (Trojan Source). — Low: notes show `\:` in source view; reading view renders `:`. |
| IP6 | **Ruling (makes IN25 hold):** the evidence block renders through a shrink ladder — (50 list entries, 256 code points per value), then (20, 256), (5, 128), (0, 64) — and returns the first result at or under 16 KiB UTF-8; the last step is within the bound for any input, pinned by a worst-case test. — Several report strings are unbounded (`export_name`, `name`, `severity`, `fallow-report-schema.ts:50,115,122`), so a 50-entry cap alone bounds nothing. — Low: a pathological finding's note shows fewer entries and shorter values than a normal one. |
| IP7 | **Ruling (sharpens IN23/IN31):** a marker is a whole line equal to the marker text; only a CR before the LF is tolerated, so an indented or trailing-space marker counts as edited. The new block takes the begin line's line ending (CRLF notes stay CRLF); everything outside the two marker lines is returned byte for byte, including an end marker on the last line with no newline. — "Exactly one begin followed by exactly one end" needs a line definition, and a tolerant match would let a marker inside prose or a code span count. — Low: a user who indents a marker must restore it before refreshing (the dialog says so). |
| IP8 | **Ruling (corrects IN38, S3):** after a refresh the human body sections are byte-identical, and the user's frontmatter keys (and `status`, `created`) are **value**-identical (compared parsed). — IN32 mandates `processFrontMatter`, which re-serialises the whole YAML block, so bytes (comments, quoting, key order of user keys) cannot be promised. — Medium: a user's YAML comments in the frontmatter are lost on refresh; recorded as a limitation. |
| IP9 | **Ruling (extends IN21/IN27, S7):** names are cut by code point; trailing dots and spaces are stripped; a Windows reserved stem is suffixed with `_` with or without an extension (`CON` → `CON_`, `nul.backup` → `nul_.backup`). The dialog's name field holds the base name; `.md` is shown as a suffix. — Windows and macOS vaults are case-insensitive while `getAbstractFileByPath` is not, and Windows silently drops trailing dots, so both would pass the pre-check and fail at `vault.create`. — Low: on a case-sensitive Linux vault, `a.md` and `A.md` get distinct names anyway (`A (2).md`). |
