## 0. Scope

The execution half of the Fallow Ingestion deliverable. Part 6 (§0) left it to this part.

- **A. Executable binding and trust (02.4).** Each codebase profile can have one bound fallow executable, stored in `data.json`. Trust is a fingerprint, remembered until something it covers changes. The S14 "installed analyzer" route is added to the Connect fallow dialog.
- **B. The async runner (02.5).** A new process adapter in `src/adapters/fallow/` runs `fallow --format json --no-cache --quiet --root <root>`. Output is bounded, and the run has a timeout, cancellation and a safe shutdown. The report text goes through the unchanged Part 6 parse, normalise and resolve pipeline (U1, U9).
- **C. Collected evidence and the surfaces.** A completed run becomes an `EvidenceReport` with origin `collected` and a verified source match. It goes into the same session-only `EvidenceRepository` (Y28). The badge, the Data & scans card, the commands and the copy follow.
- **D. Guards and side-effect tests (02.7).** The no-process guard (U42) is amended deliberately. `npm run verify` stays offline. A new opt-in `npm run test:fallow` runs the real, pinned fallow 3.27.0.

The owner approved this design at the Phase 1 review, including these choices:
- binding and trust are **per codebase profile**, in `data.json`;
- consent is **"remember until invalidated"**: the first run shows the full review, and later runs skip it until the binary, the root, the profile, the arguments or the version changes. Trust is stored as a fingerprint, never as a bare boolean;
- the real-binary tests are an opt-in `npm run test:fallow`, which fetches the pinned fallow 3.27.0 into a git-ignored `.fallow-bin/`. `npm run verify` stays offline, using a fake spawn and Node-script contract tests;
- the runner runs **`combined`** only (bare mode, no subcommand).

### Real-CLI facts this design rests on

These were probed on 2026-09-23 with the native `fallow.exe` 3.27.0, on a temporary copy of `tests/fixtures/fallow/project`. `tests/fixtures/fallow-runner/README.md` (new, Z40) records them.

| Probe | Observed |
|---|---|
| `fallow --version` | stdout `fallow 3.27.0`, exit 0 |
| `--format json --no-cache --quiet --root <p>` | exit **0 with findings present**, 13,185 bytes of stdout, 0 bytes of stderr, **no file created or changed** under the root |
| a root that does not exist | exit 2, stdout `{"error":true,"message":"invalid root path '…': … (os error 2)","exit_code":2}`, stderr empty |
| the same without `--no-cache` | writes `<root>/.fallow/.gitignore`, `.fallow/cache.bin` and `.fallow/graph-cache.bin` |
| `--fail-on-issues` | in bare/combined mode (what the runner actually uses), **ignored** — exit 0 regardless of findings; `dead-code --fail-on-issues` does honour it and exits 1, and exit 1 with valid JSON must still count as completed (corrected during execution, Part 7 ledger) |
| `FALLOW_*` variables (`FALLOW_MAX_FILE_SIZE`, `FALLOW_PRODUCTION`, `FALLOW_COVERAGE`, `FALLOW_COVERAGE_ROOT`, `FALLOW_TYPE_AWARE`, …) | change fallow's behaviour, so they are stripped |
| config files in the root (`.fallowrc.json` and others) | honoured. A remote `extends` needs `--allow-remote-extends`, which is never passed |
| bare mode | dead-code + dupes + health combined. Health may read the git history (read-only) |
| the npm package `fallow` | per-platform optional dependencies `@fallow-cli/<platform>`, each holding the native binary |

## 1. Decisions

### A. Executable binding and trust (02.4)

| # | Question | Decision |
|---|---|---|
| Z1 | Where is the binding stored? | `PluginDataShape` (`src/adapters/storage/plugin-data-shape.ts`) gains `analyzers?: unknown`. Its value is `{ [profileId: string]: AnalyzerRecord }`. The key is the profile id, which is also the `repositoryId` (Y5).<br>`AnalyzerRecord` (v1) is:<br>`{ v: 1; provider: 'fallow'; machineId: string; executablePath: string; timeoutSeconds: number; trust: AnalyzerTrust \| null }`<br>`AnalyzerTrust` is `{ fingerprint: string; version: string; grantedAt: string }`.<br>• `executablePath` is absolute, as typed, and trimmed. It is at most 4,096 characters and is accepted by `normalizeAbsolutePath` (`src/domain/path-safety.ts`).<br>• `machineId` is stamped by the adapter from `getOrCreateMachineId(app)`, never taken from the caller. This is the `LocalBinding` pattern: a record synced to another device reads as "chosen on another device" there, and is never run.<br>• `timeoutSeconds` is an integer from 10 to 1800. The default is 120 (Z10).<br>• `trust.fingerprint` is 8 lower-case hex digits (Z6). `trust.version` matches `/^\d+\.\d+\.\d+$/` and is at most 32 characters. `trust.grantedAt` is an ISO 8601 string from the Clock.<br>Nothing else is stored: no entity ids, no report, no stderr and no findings. |
| Z2 | Validating on read, and newer formats | The record schema is zod 4, `.strict()` (our own format, Y22's rule), in `src/application/analysis/analyzer-record.ts`, together with `decodeAnalyzerRecord(raw, machineId): AnalyzerBindingRead`.<br>`AnalyzerBindingRead` is one of:<br>• `{ kind: 'none' }`: no `analyzers` key, or no entry for the profile;<br>• `{ kind: 'bound'; binding: AnalyzerBinding }`: a valid v1 record stamped with this machine;<br>• `{ kind: 'other-machine' }`: a valid v1 record stamped with another machine;<br>• `{ kind: 'invalid' }`: `v` is 1, but the record fails the schema;<br>• `{ kind: 'unsupported' }`: the entry is not an object, or its `v` is not 1, or the `analyzers` value itself is not an object.<br>Write rules follow Y7:<br>• `unsupported` is **read-only**. Every write rejects with `AnalyzerStoreError('unsupported')` and the entry is never overwritten. Only a profile purge (Z11) deletes it.<br>• `invalid` and `other-machine` records are never used and are kept as they are. Choosing an executable (`bind`) replaces them, because that is an explicit user replace. Forget deletes them. Every other write rejects with `AnalyzerStoreError('not-bound')`.<br>Every write changes **only its own profile's entry**. Every other entry, valid or not, is carried over verbatim. |
| Z3 | Port and adapter | **Port:** `src/application/ports/analyzer-binding-store.ts`:<br>`interface AnalyzerBindingStore {`<br>&nbsp;&nbsp;`read(profileId): Promise<AnalyzerBindingRead>;`<br>&nbsp;&nbsp;`bind(profileId, executablePath): Promise<void>;` (replaces the path and sets `trust: null`; keeps the `timeoutSeconds` of a `bound` record, and otherwise writes 120)<br>&nbsp;&nbsp;`setTimeoutSeconds(profileId, seconds): Promise<void>;`<br>&nbsp;&nbsp;`grantTrust(profileId, trust, expectedPath): Promise<void>;` (rejects with `'changed'` when the stored path is no longer `expectedPath`)<br>&nbsp;&nbsp;`revokeTrust(profileId): Promise<void>;`<br>&nbsp;&nbsp;`forget(profileId): Promise<void>;`<br>&nbsp;&nbsp;`purge(profileId): Promise<void>; }`<br>`AnalyzerBinding` is `{ profileId; executablePath; timeoutSeconds; trust: AnalyzerTrust \| null }`.<br>`AnalyzerStoreError.code` is `'unsupported' \| 'not-bound' \| 'changed'`.<br>**Adapter:** `src/adapters/storage/plugin-data-analyzer-store.ts` exports `createPluginDataAnalyzerStore(plugin, machineId)`.<br>• Every write is **one** `writePluginDataSlice(plugin, 'analyzers', …)` under the existing plugin-wide `withDataLock`. The mutation re-decodes the entry it finds inside the lock, so a concurrent write is never silently overwritten.<br>• There is **no cache**: every `read` goes to `readPluginData`. A change made by Sync or by hand is therefore seen at the next run check (this goes further than Y19).<br>`tests/fixtures/in-memory-analyzer-store.ts` implements the same port for tests and the harness. `tests/contracts/analyzer-binding-store.contract.ts` runs against both. |
| Z4 | Which files are accepted as the executable | `src/adapters/fallow/executable-inspector.ts` exports `createExecutableInspector(deps = {})`, which implements `ExecutableInspectorPort` (`src/application/ports/executable-inspector.ts`):<br>`inspect(executablePath: string, rootPath: string): Promise<ExecutableInspection>`<br>It uses `node-access.ts`'s `fsPromises` (injectable, following M17). It never executes anything. The checks run in this order, and the first failure wins:<br>1. **absolute**: `normalizeAbsolutePath` accepts the path. Otherwise the refusal is `not-absolute`.<br>2. **name**: the base name must be exactly `fallow.exe` (Windows, compared case-insensitively) or `fallow` (elsewhere, case-sensitive). A base name `fallow` with the extension `.cmd`, `.bat`, `.ps1`, `.js`, `.mjs`, `.cjs`, `.sh` or `.vbs` (in any case) is refused as `launcher`. Any other name is refused as `wrong-name`.<br>3. **exists**: `fsPromises.stat`, which follows links. `ENOENT` gives `executable-missing`. Any other error is refused as `unreadable`, with the error code as the detail.<br>4. **regular file**: `stat.isFile()`. Otherwise the refusal is `not-a-file`.<br>5. **real path**: `fsPromises.realpath` is recorded. It is not re-checked by name, so a Homebrew-style link to a versioned binary is fine.<br>6. **native format**: the first 4 bytes of the real file are read with `fsPromises.open(real, 'r')` + `handle.read` + `handle.close`. The file must match this platform's native format: `4D 5A` ("MZ", PE) on `win32`; `7F 45 4C 46` (ELF) on `linux`; one of `FE ED FA CE`, `FE ED FA CF`, `CE FA ED FE`, `CF FA ED FE` or `CA FE BA BE` (Mach-O) on `darwin`. A file that starts with `#!` is refused as `launcher`, which is how an npm POSIX bin link to a JS launcher is caught. Anything else is refused as `not-native`.<br>On success the result is `{ ok: true; facts: ExecutableFacts }`, where `ExecutableFacts` is `{ executablePath; realPath; size; mtimeMs; format: 'pe' \| 'elf' \| 'mach-o'; insideRoot: boolean }`.<br>On failure it is `{ ok: false; refusal: ExecutableRefusal; detail: string }`, where `ExecutableRefusal` is `'not-absolute' \| 'wrong-name' \| 'launcher' \| 'executable-missing' \| 'not-a-file' \| 'not-native' \| 'unreadable'`.<br>`node-globals.d.ts` gains `realpath(path: string): Promise<string>` and `open(path: string, flags: 'r'): Promise<NodeFileHandleLike>`, where `NodeFileHandleLike` is `{ read(buffer: Uint8Array, offset: number, length: number, position: number): Promise<{ bytesRead: number }>; close(): Promise<void> }`. `node-access.ts` itself is not touched (M17). |
| Z5 | An executable inside the codebase | `insideRoot` is true when `isContained(rootPath, realPath)` or `isContained(rootPath, executablePath)`, using `src/domain/path-safety.ts` (the platform's case rule, M20). The review then shows `FALLOW_REVIEW_INSIDE_ROOT` (§2) as a warning, above the Trust and run button. The trust rules are the same: the extra copy is the safeguard, and the fingerprint (Z6) already covers the file. |
| Z6 | The trust fingerprint | `src/application/analysis/analyzer-trust.ts`:<br>`fingerprintTrust(plan: TrustSubject, version: string): string` is `fnv1a32Hex` (`src/domain/hash.ts`) over `JSON.stringify` of<br>`{ v: 1, provider: 'fallow', profileId, machineId, exe: facts.executablePath, real: facts.realPath, size: facts.size, mtime: Math.trunc(facts.mtimeMs), root: fingerprintSource(rootPath), args, version }`.<br>`TrustSubject` is `{ profileId; machineId; rootPath; args: readonly string[]; facts: ExecutableFacts }`.<br>• `fingerprintSource` is the case-sensitive one from `approval.ts` (M29's fail-safe direction: a root that only differs in case re-asks).<br>• The time limit is **not** covered. Changing it does not ask again, because it cannot widen what runs.<br>`isTrustCurrent(trust: AnalyzerTrust \| null, subject, version): boolean` recomputes the fingerprint and compares it. It is false for `null`.<br>This is FNV, not cryptography, exactly as in `approval.ts`: it detects an incidental change, and it is documented as no defence against a deliberate forgery (§6). |
| Z7 | When trust is checked, and what invalidates it | The **pre-run check** (`FallowAnalysisService.checkTrust`, Z22) runs before any execution. It reads the binding, inspects the executable (Z4), and computes `fingerprintTrust(subject, trust.version)` with the stored version. A mismatch means **review**, and nothing is executed.<br>The **post-probe check** runs after the `--version` probe (Z8), which the pre-run check authorised. If the probed version is not `trust.version`, trust is revoked (`revokeTrust`), the run ends as failed `version-changed`, and nothing is analysed.<br>Therefore, after any change to the profile, the machine, the path, the real path, the size, the modification time, the root, the arguments or the version, the review is shown again before anything else runs. `bind` always sets `trust: null`, so choosing a different executable, or the same one again, always shows the review. |
| Z8 | The version probe | The probe is `[executable, '--version']`, with the same cwd (the root), environment and spawn options as the run (Z15, Z16). It has a **5 s** timeout (`FALLOW_VERSION_TIMEOUT_MS = 5_000`), stdout is capped at **4 KB** (`FALLOW_VERSION_MAX_BYTES = 4_096`), and stderr keeps the usual tail.<br>It runs **only after the user's "Trust and run"** (first run, or after a review), or after a passing pre-run check (Z7). It is never run from a review, a settings screen, a startup or a view restore.<br>`parseFallowVersion(stdout)`, in `src/application/analysis/fallow-invocation.ts`, trims the output and matches `/^fallow (\d+)\.(\d+)\.(\d+)$/`.<br>Failures:<br>• exit ≠ 0, a timeout, a spawn failure or unmatched output gives `version-probe-failed`, with detail `'timeout'`, `'no-version'` or the exit code (a spawn `ENOENT` gives `executable-missing`);<br>• a major version other than 3 gives `version-unsupported`, with the printed version as the detail.<br>Trust is stored only when the probe passes: `grantTrust(profileId, { fingerprint: fingerprintTrust(subject, version), version, grantedAt: clock.nowIso() }, facts.executablePath)`. |
| Z9 | Tested and untested versions | `FALLOW_TESTED_VERSIONS = ['3.21.0', '3.27.0']`, in `fallow-invocation.ts`: the versions the committed fixtures were recorded with (Y20/Y21).<br>Any other `3.y.z` runs, and it is labelled **untested**: `tested: false` in the run state (Z20) and in the collected provenance (Z25), and "(untested version)" in the copy.<br>The Part 6 `(kind, schema_version)` check stays the real gate. A future 3.x that emits an unsupported schema fails with `output-unsupported` and its own message, and is never read partially. |
| Z10 | The time limit | This is a per-profile, explicit adapter setting (ST states: "actual job timeouts are explicit adapter settings"). It is `timeoutSeconds` in the record (Z1): an integer, **min 10, max 1800, default 120** (`FALLOW_TIMEOUT_DEFAULT_S = 120`, `FALLOW_TIMEOUT_MIN_S = 10`, `FALLOW_TIMEOUT_MAX_S = 1800`).<br>It is edited only in Obsidian's settings (Z12). It is shown in the review and on the card. The run captures the value at its start, and a change applies to the next run. |
| Z11 | Forgetting, and removing a profile | **Forget executable** (card, Z32; settings, Z12) calls `service.forget(profileId)`, which calls `store.forget` and deletes `analyzers[profileId]`. It is refused (`aria-disabled` plus a guarded handler, E40) while that codebase's run is active.<br>**Removing a profile** (`settings-tab.ts` `deleteProfile`): after `profileStore.remove(id)` and the review purge (Y17), it calls `service.purgeProfile(id)`. That cancels an active run for the profile (with no publication) and then calls `store.purge(id)`, which deletes the entry **whatever its format**, the same as `deleteReviewSet`. A failed purge shows `PROFILE_ANALYZER_PURGE_FAILED` through the existing `showFailure`, and the list refreshes. |
| Z12 | Settings and the disclosure | Each profile page (`buildProfilePage` in `src/host/setting-definitions.ts`) gains two rows after "Source folder":<br>• **"fallow executable"**, a custom render like `renderBindingStatusRow`. Its description is the path plus the trust state, using the card strings in §2 (`FALLOW_EXE_NONE`, `FALLOW_TRUST_VALUE`, `FALLOW_EXE_OTHER_DEVICE`, `FALLOW_EXE_INVALID`, `FALLOW_EXE_UNSUPPORTED`). A **Forget** button (`data-action="forget-analyzer"`) is added only when a record exists and is not `unsupported`. When the service answers `'busy'`, a Notice shows `SETTINGS_FALLOW_BUSY` and nothing changes. Choosing an executable is not offered here: it needs the codebase's folder and the review, which live in Data & scans.<br>• **"fallow time limit"**, rendered **only when the record is `bound`** (no disabled control). It is a number input in seconds, described as `SETTINGS_FALLOW_LIMIT_DESC`. When the service answers `'invalid'`, a Notice shows `SETTINGS_FALLOW_LIMIT_INVALID` and the stored value is put back (the M62 pattern).<br>`ProfileEntry` gains `analyzer: AnalyzerBindingRead`. `settings-tab.ts` reads it on `refresh()` through the service's `readBinding`. `SettingDefinitionsCallbacks` gains `onForgetAnalyzer(profileId)` and `onAnalyzerTimeoutChange(profileId, rawValue)`.<br>`STORAGE_DISCLOSURE_TEXT` is replaced by the text in §2. `CodebaseInspectorSettingTab`'s constructor gains a last parameter, `analysis: Pick<FallowAnalysisService, 'readBinding' \| 'forget' \| 'setTimeLimit' \| 'purgeProfile'>`. |

| Z15 | The spawn call | **`src/adapters/fallow/fallow-runner.ts`** exports `createFallowRunner(deps: FallowRunnerDeps = {}): AnalyzerProcessPort`. `FallowRunnerDeps` is `{ spawn?: SpawnLike; env?: Record<string, string \| undefined>; platform?: string; killProcess?: (pid: number, signal: string) => void; setTimer?: (fn: () => void, ms: number) => unknown; clearTimer?: (handle: unknown) => void }`. Each defaults to `node-process-access.ts` or the global timers. With `childProcess === null` (not desktop), `run` resolves `{ kind: 'spawn-failed', errorCode: 'UNAVAILABLE' }` and never throws.<br>`AnalyzerProcessPort` is:<br>`run(request: ProcessRequest, token: CancellationToken): Promise<ProcessOutcome>`<br>`killAll(): void`<br>`ProcessRequest` is `{ executablePath: string; args: readonly string[]; cwd: string; timeoutMs: number; maxStdoutBytes: number; maxStderrBytes: number }`.<br>The **one** call is `spawn(request.executablePath, request.args, { cwd: request.cwd, env, shell: false, windowsHide: true, detached: platform !== 'win32', stdio: ['ignore', 'pipe', 'pipe'] })`.<br>The adapter is generic: the application builds the argv. That is also how tests supply the executable: contract tests pass `executablePath: process.execPath` and `args: [fakeFallowScript, '--mode=…', …]` (Z38).<br>The **exact production argv** comes from `fallow-invocation.ts`:<br>• `FALLOW_RUN_ARGS(root) = ['--format', 'json', '--no-cache', '--quiet', '--root', root]`;<br>• `FALLOW_VERSION_ARGS = ['--version']`.<br>The cwd is always the root. No subcommand, no `fix`, `init`, `setup`, `watch`, `--fail-on-issues`, `--allow-remote-extends` or `npx` ever appears (Z38 tests this). |
| Z16 | The environment | The child gets a **built** environment, never `process.env` as it is. `FALLOW_ENV_ALLOW_LIST` in `fallow-invocation.ts` is `['PATH', 'SystemRoot', 'TEMP', 'TMP', 'TMPDIR', 'HOME', 'USERPROFILE', 'LOCALAPPDATA']`, plus `FALLOW_ENV_EXTRA = { NO_COLOR: '1' }`.<br>`buildChildEnv(source, platform)` in `src/adapters/fallow/process-output.ts`:<br>• copies each allow-listed name that has a value. On `win32` the lookup is case-insensitive over `source`'s own keys (so `Path` fills `PATH`), and the key is written in the list's spelling;<br>• adds `NO_COLOR=1`;<br>• drops, as a second guard, any key starting with `FALLOW_` or equal to `NODE_OPTIONS`, even if a future list edit admitted it.<br>Proxy variables, `NODE_*`, `npm_*` and every other variable are therefore absent. |
| Z17 | Bounded output | In `src/adapters/fallow/process-output.ts` (pure, no Node import):<br>• `createStdoutCollector(maxBytes)` keeps `Uint8Array` chunks while their total is at most `maxBytes`. The chunk that would cross the cap flips `overflowed`, is not kept, and makes the runner kill the child (Z17a). The cap is `FALLOW_REPORT_MAX_BYTES` (16 MB, Y20), in **bytes**. `text()` decodes with `new TextDecoder('utf-8', { fatal: true })` and returns `null` for invalid UTF-8.<br>• `createStderrTail(maxBytes)` keeps only the **last 64 KB** (`FALLOW_STDERR_TAIL_BYTES = 65_536`). `excerpt()` decodes it non-fatally, removes ANSI escape sequences (`/\x1b\[[0-9;?]*[ -\/]*[@-~]/g`), turns every other C0 control except `\t` and `\n` into nothing, and returns the text.<br>stderr is never parsed and never mixed into stdout. It is kept in memory only, for a failed run's log excerpt (Z33), and is never persisted.<br>**(Z17a)** Reaching the cap kills the child exactly as a timeout does (Z18), and the outcome is `stdout-too-large`. No partial stdout is ever parsed. |
| Z18 | Timeout, cancellation and killing | The adapter owns the timers. The application has none.<br>• **Timeout:** `setTimer(…, request.timeoutMs)` starts at spawn. When it fires, the child is killed and the outcome is `timed-out`.<br>• **Cancel:** `token.onCancelled` kills the child, and the outcome is `cancelled`. A token already cancelled before spawn means spawn is never called, and the outcome is `cancelled`.<br>• **Kill (cancel, timeout or cap):**<br>&nbsp;&nbsp;– POSIX: `killProcess(-pid, 'SIGTERM')` to the whole process group (the child is a group leader through `detached: true`), then `killProcess(-pid, 'SIGKILL')` after a **2 s** grace (`FALLOW_KILL_GRACE_MS = 2_000`) if `exit` has not arrived;<br>&nbsp;&nbsp;– Windows: `child.kill()`, which is TerminateProcess on the **direct child only**. No `taskkill` is spawned (§6). The same grace applies, then `child.kill()` again.<br>• **Resolution:** a killed run resolves on `exit`, after `stdout.destroy()` and `stderr.destroy()`, so a grandchild holding the pipes cannot keep the run open. A normal run resolves on `close` (every pipe drained). ## 6. Limitations

These are written into `2026-09-17-wp01-limitations.md`:

- **No process-tree kill on Windows.** `child.kill()` ends the direct `fallow.exe` only. A process it started itself could outlive a cancel, a timeout or a shutdown. No `taskkill` is spawned, to keep the process surface to one executable.
- **Not a sandbox.** An authorised fallow runs with the user's permissions and can read and change anything the account can. Trust is an application safeguard, and its FNV fingerprint detects incidental change, not deliberate forgery.
- **Config files in the root are honoured.** A `.fallowrc.json` or other fallow configuration in the analysed folder changes what fallow reports. It is not recorded in the provenance. Remote `extends` is never fetched.
- **The git history may be read.** Health analysis may read the repository's git data (read-only).
- **Scan exclusions do not apply to fallow.** fallow reads the whole folder. Findings in excluded files come back as unmatched paths and never paint the city.
- **Untested versions.** Only 3.21.0 (fixtures) and 3.27.0 (fixtures and `test:fallow`) are tested. Other 3.x versions run labelled untested, and the side-effect claim ("writes nothing") is verified for 3.27.0 only.
- **A force-quit mid-run.** If Obsidian is killed without `onunload`, a running fallow is not stopped by the plugin and runs until it finishes on its own.
- **The final parse is synchronous.** `JSON.parse` of a report of up to 16 MB runs on the UI thread, as a Part 6 import does. It is measured, not bounded.
- **Machine identity is inferred.** The "another device" rule relies on `loadLocalStorage` not being synced (the existing `getOrCreateMachineId` risk).

## 7. Out of scope

- Watch mode, and any background or automatic re-run.
- Other providers, and other fallow subcommands run individually (`dead-code`, `health`, `dupes`): the runner runs combined only.
- Installing, updating or downloading fallow from the plugin, `npx`, or bundling a binary.
- `fix`, `init`, `setup`, auto-fix, source deletion, and `--fail-on-issues`.
- Persisting collected evidence across a restart, and findings history (Snapshot History).
- Surfacing the fallow sections Part 6 lists as not shown.
- Windows process-tree killing (`taskkill`, job objects).
- `.cmd` or `.ps1` launchers, or any shell execution.
- Choosing fallow flags, config files or production mode in the UI.
- Reacting to external `data.json` changes beyond the per-check re-read (Z3).
- A running-analysis indicator on the city's own StatusBanner or toolbar.

## 8. Decisions taken while writing (for owner review)

1. The executable must pass a **native magic-byte check** (PE, ELF or Mach-O, first 4 bytes); `#!` files are refused as launchers (Z4). This catches npm's POSIX JS bin link.
2. The binding and trust are **stamped with the machine id** and ignored on another device (Z1).
3. The **time limit is not part of the trust fingerprint** (Z6). Its range is **10–1800 s** (Z10).
4. **`TMPDIR`** joins the environment allow-list for POSIX (Z16).
5. The time limit and Forget live in **Obsidian's settings**. Choosing an executable happens only in Data & scans (Z12).
6. `FallowRunErrorCode` sits **beside** `FallowImportErrorCode`, with a mapping for output-parse codes (Z19).
7. The collected provenance is an **optional `collected` field**. `fileName` holds the executable's base name, and `importedAt` keeps its name, meaning "attached at" (Z25).
8. "Marks it stale" is an **`EvidenceRepository.markStale` port method** plus an optional `staleReason: 'failed-run'` (Z23).
9. A run whose evidence changed mid-run is **discarded as `superseded`**. Import, Remove, Change and Forget are blocked while a run is active (Z20, Z32).
10. A start from a leaf whose snapshot is not the codebase's latest is **refused as `snapshot-changed`** (Z22).
11. `run` and `trustAndRun` **resolve at start**, and the run continues detached (Z21, Z22).
12. There is **no plugin-wide cap** on concurrent runs across codebases (Z21).
13. The kill grace is **2 s** (SIGTERM, then SIGKILL on POSIX), a close grace of 2 s gives `output-incomplete`, and `onunload` sends **SIGKILL immediately** (Z18).
14. The run banner lives on the **Data & scans card only**. Operational failures also raise a **Notice** (Z33, Z34).
15. The **Planned integrations panel is removed**, not reworded (Z32).
16. **`FALLOW_BIN`** lets `test:fallow` use a local binary. The fetch uses `npm install --prefix .fallow-bin --no-save --no-package-lock --ignore-scripts` through `npm_execpath`, with no shell (Z40).
17. `assert-bundle.mjs` asserts **exactly one** `node:child_process` literal in `dist/main.js` (Z38).
18. The no-freeze evidence gate is **an event-loop gap under 50 ms** while the child runs. The final parse is measured only (Z38).
